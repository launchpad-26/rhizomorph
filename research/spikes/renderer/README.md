# The renderer spike (#566)

Throwaway measurement rig for prd-33 ruling 11. The finding lives in
[`research/2026-08-15-renderer-spike.md`](../../2026-08-15-renderer-spike.md);
this directory is only how it was obtained.

**Nothing here is imported by the app, and nothing in `packages/web/src/scene/`
was modified.** The spike imports the real scene *read-only* and adds a second
painter beside it.

## Running it

```
node research/spikes/renderer/run.mjs            # the matrix, 30 s × 3 runs
node research/spikes/renderer/run.mjs --quick    # one 3 s run per cell
node research/spikes/renderer/run.mjs --shots    # one frame per arm, as PNG
```

Writes `results.json` beside this file. `bench.js` is generated by esbuild on
every run and is gitignored.

## What each file is

| file | what it is |
| --- | --- |
| `scene.ts` | The shared model. Imports the **real** `layoutScene` + `sceneMarks`, places three colonies, and adds prd-33's material load. Both arms consume its output unchanged. |
| `webgl.ts` | The WebGL2 painter, written for this spike. |
| `bench.ts` | The harness: warm-up, control, stream and paced measurement. |
| `run.mjs` | Bundles, serves, drives Chromium, collects JSON, measures bundle cost. |
| `shot-*.png` | One frame from each arm. The parity evidence. |

The canvas 2D arm is `packages/web/src/scene/paint.ts` itself, called directly.
It is not a re-implementation, which is the point: one arm is the shipping
painter.

## Three things about the rig that a reader has to know

**Chromium runs headful.** Headless on this box falls back to SwiftShader —
software rasterisation — which would have measured a CPU rasteriser in both arms
and called it a GPU comparison. `run.mjs` refuses a result whose
`UNMASKED_RENDERER_WEBGL` names a software device.

**The frame is not paced by `requestAnimationFrame`.** Under WSLg an *empty*
rAF callback returns a median period of 34.4 ms whatever the page draws, and
`--disable-gpu-vsync --disable-frame-rate-limit` do not lift it. Read off that
clock both arms would have measured 29 fps and the spike would have concluded
nothing. See the header of `bench.ts` for what replaced it.

**The two arms' sync primitives are not comparable per-frame,** so they are not
compared that way. A canvas `getImageData` costs ~150 ms of GPU→CPU readback
under WSL2 and repeated readback demotes the canvas to software raster; a WebGL
`clientWaitSync` does neither. The headline metric therefore syncs **once per
run** and divides elapsed by frames. The per-frame variant is reported beside it
as the diagnostic that shows the asymmetry rather than hiding it.
