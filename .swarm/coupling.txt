# Coupling points — files a fence cannot see coming.
#
# `scripts/fence-lint.sh` reads this before a wave is dispatched. For each path
# below it asks whether any issue in the wave fences it, and warns when the wave
# is working inside its subtree without owning it. Until this file existed the
# lint exited 1 with "create one", so the repo's pre-dispatch check was dead.
#
# FORMAT, one entry per line, exactly as fence-lint.sh parses it:
#
#     <path>  # why it couples
#
# One path per line — the path is everything before the first `#`, trimmed, and
# the whole rest of the line is the reason, printed verbatim in the warning. A
# line starting with `#` in column 1 is a comment; blank lines are skipped. An
# entry with no reason is worse than no entry: the reader has to go and find out
# what couples before they can judge the warning, and a warning nobody can judge
# is a warning everybody learns to skip.
#
# What belongs here: a file that a change ELSEWHERE forces an edit to. Not a
# file that is merely popular. The test is whether a lane could do everything
# right inside its own fence and still redden this file.

# ── the containment ratchet's exact count over other directories' tests ─────
# The falsifier this entry was written against: if the honest reason were "any
# test file anywhere may trip this", it would be a repo-wide lint and the rule
# would belong in the law's own failure message rather than in this registry.
# VERDICT: it is a coupling. The sweep is bounded to `.test.ts` files under
# packages/server/src (packages/web is not swept at all), and a line only counts
# when it matches one of the detector's five shapes AND sits near a `node:path`
# call. That nearby-path test is a PROXY, not a semantic one, so "ordinary string
# parsing is not a hit" is true only usually: EXECUTED, a git-porcelain
# `line.startsWith(marker)` with an unrelated `path.resolve` one line above IS
# counted, and the same line alone is not. The law's doc comment records that
# coincidence as an accepted residual. What makes it a coupling
# is that every site it counts sits in some OTHER directory while the pin lives
# in paths/.
#
# The residual, stated because it is the reverse of the risk this file's header
# names: the lane most likely to trip this — one fenced on a single new test
# file somewhere else under packages/server/src — gets `info` out of fence-lint,
# never a warning. That is the section's shape rather than this entry's: a fence
# containing an entry's own directory reports it `ok` (owned), and the WARN
# branch is unreachable altogether, which scripts/dev/coupling.test.sh already
# asserts and records as deliberate. EXECUTED here over prd17 wave 7 and prd53
# wave 3 — `info` in both. So this entry earns its place as the grep-able
# explanation the red bar itself does not carry, which is how #258's plan author
# found the coupling at all; putting the same guidance into the law's own failure
# message would reach a lane that has already gone red, and is a follow-up
# outside this fence.
packages/server/src/paths/prefix-comparison-law.test.ts  # `.toBe(TEST_FILE_KNOWN_DEBT_COUNT)` pins an exact count of containment-shaped sites in every `.test.ts` AND `.test.tsx` under packages/server/src, its own file excepted — the law skips itself by name because its rigged snippets are string literals carrying the very idioms it hunts (EXECUTED: a `.test.tsx` plant IS counted, so "every .test.ts" understates the sweep in one direction and overstates it in the other). The assertion is cited by symbol because the pin is written against the constant and never against the literal; the constant stands at `const TEST_FILE_KNOWN_DEBT_COUNT = 14` today, which is an as-of value rather than a quotable form. The 14 are spread across seven files in api/, concierge/, lab/, recorder/ and server/, and none of them in paths/, so every site the pin counts belongs to some other lane's fence. It fails in BOTH directions, like theme/tokens.test.ts and api/route-class-law.test.ts above: writing the obvious `file.startsWith(dir + path.sep)` in a new test reddens paths/ from a directory the lane never entered, and legitimately RETIRING a site does too — the pin is deliberately not a ceiling. EXECUTED both ways: planting one site takes the count to 15, and retiring one — migrating `lab/fork.test.ts`'s single site to a `.split(path.sep).includes(...)` spelling — takes it to 13, both red. But be exact about what the exact pin closes, because the law is: it closes a migration made ALONE. A migration PLUS one new site in the same change still cancels out at 14 and stays GREEN, exactly as it did under the old `toBeLessThanOrEqual` ceiling — the law's doc comment states that itself, confirms it as a mutation, and accepts it as a residual on the grounds that commit-by-commit review catches what a count cannot. EXECUTED in #258: a first draft of shipper/hand-law.test.ts used that spelling in five places and the suite came back "test-file containment sites: 19, pinned: 14" from a fence that named one new file, and the pin was outside it. WHAT TO WRITE INSTEAD, none of which the detector counts — a `Set` of canonical paths built by walking the real tree plus `set.has(file)`; `isInside(parent, candidate)` from paths/containment.ts, the shared primitive this law exists to protect; or an explicit array of paths with `.includes(...)`. Note what IS and is not a hit, because getting this backwards sends you straight into the red bar, and because for the fifth shape the answer is POSITIONAL rather than about the receiver. A string-literal argument clears the first four shapes, which need an identifier or a root-shaped template, so `specifier.startsWith('.')` is safe outright. The fifth shape never looks at the receiver at all — `RELATIVE_FOLLOW_RE` matches a bare `.startsWith('..')` anywhere in its window — so even `specifier.startsWith('..')` on a module specifier IS a hit when it lands inside the window of ANY `path.relative(` call. EXECUTED: a `relative()` helper with `specifier.startsWith('..')` four lines below it takes the count to 15; eleven lines below leaves it at 14. `.startsWith('..')` on a `path.relative` result is the same fact stated from the other end, and it IS a hit. That is the fifth shape, `relative-startsWith-dotdot`: it fires when a `path.relative(` call — or `path.posix.relative(`, which `RELATIVE_RE` covers too — is followed by `.startsWith('..')`, `path.isAbsolute(`, or the `.split(path.sep)[0] !== '..'` spelling anywhere in a window of RELATIVE_WINDOW lines that INCLUDES the call line. So: the same line, or up to SIX lines after it, and a seventh line clear. EXECUTED at the boundary, because "within 7 lines" is the off-by-one this sentence invites: a follow-up six lines after the call takes the count to 15, seven lines after leaves it at 14. It is the idiom all three production allowlist entries carry, so reach for `isInside()` rather than `path.relative` + `'..'`. #258's plan comment asserts the opposite, as EXECUTED. Its conclusion was right for the one file that plan fenced — `shipper/hand-law.test.ts` DOES make a `path.relative` call, in its `relative()` helper, but carries no dotdot, `isAbsolute` or `split` follow-up within the window of it, so nothing there could fire — while its stated REASON is false as the general rule it reads like. Note how narrow that escape was: a `specifier.startsWith('..')` written within six lines of that helper would have reddened it. This entry is the correction, and the reason a claim like it belongs in the registry rather than in a merged PR's prose. If the count must genuinely move, edit the pin AND correct the reasoning in the doc comment beside it in the same commit — that comment names isInConcierge, resolvesIntoServerLab and findOutsideReferences as the intended migration targets, and migrating any one of them lowers the number.
