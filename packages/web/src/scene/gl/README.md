# The WebGL2 painter (#578, ADR-0021)

The executor, replacing `paint.ts`. The display list does not change: `sceneMarks`
returns the same plain data it always did, `marks.test.ts`'s 153 encoding laws did
not move, and `palette.ts`'s mirror was not touched — the painter consumes the same
`Rgb` constants and divides by 255.

| file | what it is |
| --- | --- |
| `frame.ts` | **the display list → triangles and draw ranges.** Pure; no context anywhere |
| `batch.ts` | the vertex stream and the run list |
| `tessellate.ts` | geometry: the ribbon zip, the stencil fans, polylines, falloff quads |
| `programs.ts` | three GLSL programs, their uniforms, and the grain's noise tile |
| `painter.ts` | upload, submit, and the context-loss recovery path |
| `overlay.ts` | the transparent 2D canvas that carries `text`, `path` and `chip` |
| `recorder.ts` | a WebGL2 context that records instead of rasterising, for tests |
| `index.ts` | `createScenePainter` — the one thing `useFrameLoop` calls |

Two things are worth knowing before reading any of it.

**The order is the display list's order.** The spike sorted the frame into two
batches by blend class and drew it in two calls. Additive does not commute with
source-over, so that is a reordering and it changes the picture — a halo canvas
paints *under* the root-mass comes out on top of it. Here the whole frame is one
upload and the run list records where the blend or the transform changes. This
scene costs 44 runs and 66 draw calls, against several hundred canvas fills.

**The painter is cut in two at the GPU.** Everything that decides what the picture
*is* runs in `frame.ts`, over plain arrays, with no context — so it runs in the
suite at full fidelity. See "the testability cost" below.

## The five debts ADR-0021 booked

### 1. Type and glyphs — **overlay, not an atlas**

`text`, `path` and `chip` go on a transparent 2D canvas layered over the GL one.

Which means `overlay.ts` is where the scene's **type stacks** live now, and they
are a mirror of `--font-sans` / `--font-mono` in `theme/theme.css`, character for
character — `ctx.font` takes a string and canvas cannot read a custom property.
`FONT` is exported for `palette.test.ts`, which holds it to the tokens, and that
mirror is load-bearing rather than decorative: #548 found both stacks had already
drifted (sans naming no Inter at all, mono listing JetBrains Mono *fourth*), so
the scene would have painted in system faces while the DOM used the real ones.
Moving the record between files is exactly where such a mirror dies quietly, so
the assertions were repointed here and nothing about them was relaxed.

An atlas would have to carry `ui-sans-serif` and `ui-monospace` — two *system*
stacks the browser resolves to whatever the machine has — at every size the scene
draws, rebuilt on DPR change, and law 11's "tabular numerals" clause is a property
of the face rather than of the raster. Baking that means shipping a font (weight
this repo removed `three` to avoid) or rasterising the system one at runtime, which
is the overlay again with extra steps. The spike measured the overlay at 0.4 ms for
215 glyph paths against a 16.67 ms budget.

**The compositing order, explicitly:**

1. the GL canvas draws the world through the camera, then the chrome washes and
   the grain at device scale;
2. the overlay, on top and transparent, draws the world's type through the same
   camera and then the gap voice at device scale.

Two surfaces means the chrome cannot dim what is above it, and the fog and the
vignette are exactly the chrome that used to dim labels near the rim. That is not
left as a delta: `veilOf` folds the chrome stack into each overlay mark's own ink,
and the algebra is exact — with the mark's alpha unchanged, `T′ = T·k + c` makes
the two composites identical, where `k` is what the chrome transmits and `c` is
what it adds. The one approximation is that it is evaluated per mark rather than
per pixel; a wash moves about 0.4% of its span across a 40 px label. The gap voice
is *excluded*, because canvas drew the gap voice after the fog too — law 12's
caveat was never dimmed and still is not.

### 2. Grain — **implemented**

`programs.ts`'s third program. The tile is a texture generated by the same
deterministic xorshift walk `paint.ts` wrote into an `ImageData`, so the print
carries the same grain it always did rather than a new noise that merely looks
similar (`noiseTile`, pinned in `frame.test.ts`). Uploaded once per tile size,
`REPEAT`-wrapped, and offset by the mark's own `tick` on both axes — the same
`x, 7x` crawl.

### 3. Even-odd — **a stencil pass, so the constraint is removed rather than made explicit**

The spike fanned contour rings from their centroid, which is correct only for rings
that are star-shaped about their centre; `contour.ts` does not guarantee that and
could not cheaply be made to. Both remedies were on the table and the stencil is the
one that leaves no new constraint behind.

Rings go into the stencil buffer with `INVERT` — one bit flipped per ring covering
a pixel — and then the bounding box is drawn wherever the bit survived, zeroing it
as it goes. A pixel inside an odd number of rings is painted and one inside an even
number is not, for any rings whatever their shape, winding or nesting. No clear
between regions; a mass with twenty shells costs twenty of these and nothing else.

The same pass takes the zero-width `regionMark` case (the rank enclosure), which is
a closed ring with no spine to zip against and therefore no reason to be assumed
star-shaped either.

### 4. `perfect-freehand`'s caps — **kept, by filling the outline**

The spike built triangle strips off the mark's *spine* and its two encoded widths.
That loses the rounded reversal caps, and — worse, and unremarked in the spike —
it loses the **pinches and the dashes too**: `widthRoot`/`widthTip` describe a
linear taper, so a frozen lane's severed thread would have been drawn as one
continuous healthy thread and the severing would have been invisible.

So `frame.ts` fills `mark.outline` — the polygons `paint.ts` filled, unchanged.
A general triangulator is O(n²) over 32k outline vertices a frame; the **zip** is
O(n), because a stroke outline is not a general polygon. `getStroke` returns the
left side forward, the end cap, the right side backward and the start cap, so
vertex 0 and vertex n−1 sit either side of the start cap and two walks from there
both run to the far end. The zip advances whichever chain is behind *in arc length*,
which is what makes it robust to the two sides carrying different vertex counts
(they always do). `frame.test.ts` pins that the emitted vertex set is exactly the
authored one — nothing invented, nothing dropped, which is the caps.

### 5. Context loss — **handled and tested**

A 2D context lives as long as its element; a WebGL context is a lease the
compositor takes back on a driver reset, a GPU hang, an adapter switch, or too many
contexts on a page. Everything the painter owns on the GPU lives in one `Resources`
record: on `webglcontextlost` the record is dropped and drawing stops, on
`webglcontextrestored` it is rebuilt from nothing and drawing resumes.
`preventDefault()` on the lost event is load-bearing — without it the browser never
fires the restore and the panel stays black for the rest of the session, which for
a read-only observer is a silent lie about the fleet rather than a visible failure.
`useFrameLoop` puts law 12's voice on it either way. `painter.test.ts` drives the
whole cycle against the recording context.

## The testability cost, and what was bought back (#244)

ADR-0006 accepted "the canvas draw path is untestable in jsdom" **because**
`node-canvas` was the named escape. jsdom 30 returns `null` for `webgl`, `webgl2`
*and* `2d`, so neither painter rasterises here — but the 2D painter had a way out
and a GL painter has none. This swap spends that escape hatch, and #244 records it.

What it buys instead is a seam the 2D painter never had. A GL context's meaning
lives in its call sequence — which program, which blend function, which stencil op,
how many vertices from which offset — so `recorder.ts` is not a shadow of the real
submission, it *is* the submission. And everything above `bufferData` is arithmetic
over plain arrays, so `frame.test.ts` asserts the geometry itself rather than that
a `fill()` was issued. Against canvas, "two hairline rings on the mass's rim" had to
be inferred from a journal of `ctx.arc` calls; it is now a query over the marks.

The one thing that genuinely cannot be asserted here is the raster, and that is
what `../parity/` is for.

## Parity

`../parity/` holds the seeded scene, the capture harness, and the committed
before/after/diff PNGs. The "before" arm is `paint.ts` itself, fetched out of git
history at capture time. Latest run, 1100×620 at dpr 2, 155 marks, ANGLE/D3D12 on
an Intel Iris Xe:

| | |
| --- | --- |
| mean channel delta | **1.30 / 255** |
| pixels differing by more than 8 | **0.36%** |
| pixels differing by more than 32 | **0.04%** |

The residue is glyph edges (text anti-aliased onto a transparent layer and then
composited is not bit-identical to text drawn straight onto the picture), ribbon
edges at the MSAA/analytic-AA boundary, and the grain's per-pixel noise where the
overlay carries its mean instead.

Two defects were found by the capture and by nothing else, which is the argument
for having it:

- **glows were drawn with the mote's curve.** `paint.ts` draws a `glow` as a
  two-stop gradient — linear in alpha — and a mote as a sprite walking `(1 − t)²`.
  Collapsing them to one curve made every halo in the scene dimmer and tighter.
  Mean delta 5.10 → 1.50.
- **stencil geometry leaked into the run before it.** A triangle run left open
  when the fans and cover box were appended was sealed at the stream's length and
  swallowed them, painting every contour's bounding rectangle over the picture.
  Neither is the kind of thing anyone reasons their way to. Both now have tests.

## Cost, reported and not asserted

The build stage — the display list to triangles, which is all of what the suite can
time — is **0.96 ms** for this scene's 155 marks and 27,114 vertices, in node.
Split: ribbons 0.48 ms (73 marks, 12,348 vertices), the root-mass contour and its
shells 0.17 ms (9,570), the rest under 0.1 ms each.

In the browser, `painter.paint()` end to end (build, upload, 66 draw calls, and the
44 overlay marks) is **~2.5 ms** median CPU, 3.0 ms wall over 120 frames.

**Scaled honestly:** the spike's decision workload is 1060 marks at 30 lanes × 3
colonies, where its WebGL arm's whole submit stage measured 2.7–3.0 ms. This
painter's ribbon path costs about 6.8 µs a mark, so 646 ribbons alone is ~4.4 ms —
call it **two to three times the spike's submit stage**, on top of an unchanged
8.8–10.3 ms model stage. That is the price of the debts above: the spike's arm did
not fill outlines, did not carry pinches, did not do even-odd and did not draw
grain. It does not touch ADR-0021's decision — canvas needs 127.8 ms for the same
frame — but prd-33 should size its fidelity work against these numbers rather than
against the spike's, and the vertex format (10 floats, of which 4 are used only by
glows and motes) is the obvious place to look first if that stage needs to come
down.
